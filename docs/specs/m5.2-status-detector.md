# Techspec — M5.2: detector de status da sessão

Escrita depois da M5.1 (`3d8c6e1`), sobre o código como ele ficou. Esta spec é **normativa**: onde ela decide, não há escolha a fazer.

O `milestones.md` não marca a M5.2 com ⬥. Ela ganhou spec por dois motivos. Primeiro, o sinal que o parser da M5.1 espera **não chega** do `claude` rodando no TermHub (seção 1). Segundo, a heurística óbvia, "saída parada = esperando", pinta de amarelo todo shell comum, e o dono decidiu o contrário (seção 2).

A M5.2 entrega um módulo puro, `packages/daemon/src/status-detector.ts`. Ninguém o chama ainda: ligá-lo à sessão, ao protocolo e à store é a M5.3.

## 1. O que o `claude` manda para o TermHub: nada, por padrão

Conferido na documentação do Claude Code (`code.claude.com/docs/en/settings-reference`, `hooks`, `terminal-config`), versão instalada `2.1.283`:

- `preferredNotifChannel` tem default `"auto"`. No `"auto"`, o `claude` manda notificação só no iTerm2, no Ghostty e no Kitty, toca o bell só no Terminal.app, e **não faz nada nos outros terminais**. O TermHub é um terminal desconhecido. Resultado: **nem BEL, nem OSC 9, nem OSC 777**.
- A barra de progresso (OSC `9;4`) sai só no ConEmu, no Ghostty ≥ 1.2 e no iTerm2 ≥ 3.6.6. No TermHub, não sai.
- Nenhuma variável de ambiente muda o canal. Só o `settings.json` do usuário, ou `--settings` na linha de comando.
- Quando o canal está ligado, o sinal sai cerca de **6 s** depois de um pedido de permissão parado, e cerca de **60 s** depois do fim da resposta. Em ambos os casos, só se o usuário não digitou nesse meio-tempo.
- O `claude` atualiza o título (OSC 0) e anima um spinner enquanto trabalha. Mesmo com `prefersReducedMotion`, o contador de segundos se redesenha a cada segundo. Trabalhando, ele não fica mais de ~1 s sem escrever.

**Decisão do dono** (26/09): o TermHub **não** mexe na configuração do Claude Code, nem no `settings.json` nem no comando de lançamento. A documentação do projeto recomenda `"preferredNotifChannel": "iterm2"`, que manda OSC 9, e o parser da M5.1 e o ConPTY já tratam. O detector funciona sem isso e fica mais rápido e preciso com isso.

## 2. A decisão do dono sobre saída parada

Sem sinal explícito, **saída parada** é classificada pela **origem da sessão**:

- Sessão lançada com `command` (M4.7, `SessionSummary.command`, por exemplo `claude`): saída parada é **`awaiting-input`**, amarelo e com toast.
- Sessão sem `command` (shell comum): saída parada é **`idle`**, cinza e sem toast.

Sinal explícito (BEL, OSC 9, OSC 777) leva a `awaiting-input` em **qualquer** sessão. Marca de prompt (OSC 133) leva a `idle` em qualquer sessão.

Limitações aceitas, e ditas com todas as letras para ninguém "consertar" em silêncio:

- **`claude` digitado à mão num shell comum** fica cinza quando para, a menos que mande sinal (seção 1).
- **O agente que saiu.** A M4.7 executa o `command` digitando-o no shell (`registry.ts`: `session.write(command + '\r')`). Quando o `claude` sai, o shell continua vivo, com o prompt. Numa sessão com `command`, esse prompt parado vira `awaiting-input`, a menos que o shell emita OSC 133 (seção 3.3). O prompt está esperando input, então o amarelo não chega a ser mentira. O conserto de verdade (o TermHub injetar shell integration nos shells que abre) fica fora de escopo.

## 3. Três defeitos que esta spec evita

### 3.1 O eco da digitação vira "rodando"

Cada tecla que o usuário digita volta como saída: o eco do shell, ou o redesenho do campo de entrada do `claude`. Contada como atividade, cada tecla faz o badge piscar de amarelo para verde e voltar, e a M5.5 dispararia um toast a cada pausa na digitação. Pior: o BEL que o PSReadLine toca quando o autocompletar falha viraria "esperando input".

**Saída e BEL que chegam dentro de `ECHO_WINDOW_MS` depois de um input do usuário não contam.** Cada input novo estende a janela.

### 3.2 O resize vira "rodando"

Redimensionar faz o ConPTY repintar a tela e o TUI se redesenhar. É saída sem trabalho nenhum. Arrastar a borda da janela ou de um split marcaria todos os agentes visíveis como rodando. **Saída que chega dentro de `RESIZE_WINDOW_MS` depois de um resize não conta.** BEL nessa janela conta: resize não toca bell.

### 3.3 O sinal explícito apagado pela saída seguinte

O ConPTY entrega BEL e OSC 9/777 **fora de ordem** em relação ao texto do mesmo quadro (`docs/specs/m5.1-osc-parser.md`, seção 1). Se o detector processasse "sinal → `awaiting-input`" e depois "saída do mesmo chunk → `running`", o sinal se perderia sempre. **Um chunk que traz BEL ou notificação resulta em `awaiting-input`, qualquer que seja o resto do chunk**, e esse estado é **fixo**: saída posterior não o tira dali, só input do usuário, marca OSC 133 ou saída do processo.

## 4. A decisão: implemente exatamente assim

### 4.1 Superfície

```ts
import type { SessionStatus } from '@termhub/shared';
import type { TerminalSignal } from './osc-parser.js';

export const DEFAULT_QUIET_MS = 3_000;
export const ECHO_WINDOW_MS = 250;
export const RESIZE_WINDOW_MS = 500;

export interface StatusDetectorOptions {
  /** True when the session was created with a `command` (M4.7). Decides what silence means. */
  agent: boolean;
  /** Silence needed before leaving `running`. Defaults to `DEFAULT_QUIET_MS`. */
  quietMs?: number;
}

export type StatusListener = (status: SessionStatus, since: number) => void;

export class StatusDetector {
  constructor(options: StatusDetectorOptions);
  /** Current status. Starts as `running`. */
  get status(): SessionStatus;
  /** Epoch ms of the last transition (construction time at first). */
  get since(): number;
  /** One output chunk arrived, with the signals the M5.1 parser found in it. */
  onOutput(signals: readonly TerminalSignal[]): void;
  /** The user sent input (keystrokes or paste) to the session. */
  onInput(): void;
  /** A client resized the session. */
  onResize(): void;
  /** The process exited. Terminal: every later call is a no-op. */
  onExit(): void;
  /** Called synchronously on every actual transition, never for a repeat. Returns an unsubscribe function. */
  onChange(listener: StatusListener): () => void;
  /** Cancels the timer. Every later call is a no-op. */
  dispose(): void;
}
```

Contrato:

- **Síncrono e sem exceção.** Todo método roda dentro de `onData`, do handler de input ou do de resize. Um listener que lança não impede os outros listeners, e não sobe para quem chamou: capture a exceção e siga.
- **Tempo por `Date.now()` e `setTimeout`/`clearTimeout` globais.** Nada de relógio injetado: os testes usam os fake timers do Vitest, que controlam os dois.
- **Um timer só** por instância, o de silêncio, rearmado a cada saída que conta. Sem `setInterval`. **O construtor já arma o timer**: a sessão nasce `running`, e um shell que nunca escreve nada não pode ficar verde para sempre.
- `quietMs` fora de um inteiro positivo cai no default. O limiar por perfil vindo do `config.json` fica fora de escopo (seção 6): a opção existe para a M7.1 ligar depois.

### 4.2 Estado interno

Além do `status`, o detector guarda:

- `sticky: boolean`: o `awaiting-input` atual veio de sinal explícito (seção 3.3);
- `lastMark: 'A' | 'B' | 'C' | 'D' | null`: a última marca OSC 133 vista;
- `echoUntil`, `resizeUntil`: instantes até onde a saída não conta;
- o timer de silêncio.

"Em prompt" quer dizer `lastMark` em `A`, `B` ou `D`.

### 4.3 As regras, na ordem em que se aplicam

**`onOutput(signals)`**, com `now = Date.now()`:

1. `exited` ou `disposed`: nada.
2. Atualize `lastMark` com a **última** `shell-mark` do chunk, se houver. Marcas de shell chegam na ordem (M5.1, seção 1), então a última do chunk é a vigente.
3. Existe no chunk algum `notification`, ou algum `bell` com `now >= echoUntil`? Então `sticky = true`, cancele o timer, e vá para `awaiting-input`. Fim.
4. O chunk tem `shell-mark`?
   - Última marca `A`, `B` ou `D`: `sticky = false`, cancele o timer, e vá para `idle`. Fim. A saída do próprio chunk (o texto do prompt) não conta.
   - Última marca `C`: `sticky = false`, vá para `running` e rearme o timer. Fim.
5. `sticky`: nada. Saída não tira de `awaiting-input` fixo.
6. `now < echoUntil` ou `now < resizeUntil`: nada. É eco ou repintura (seções 3.1 e 3.2).
7. Saída que conta: vá para `running` e rearme o timer.

Título e progresso não têm regra própria: contam como saída comum, no passo 7. O título animado do `claude` é trabalho.

**Timer de silêncio disparado:**

- em prompt (`lastMark` em `A`, `B`, `D`): `idle`;
- `lastMark === 'C'` e sessão **sem** `command`: continua `running`, porque o shell disse que um comando está executando. Não rearme: a próxima saída rearma;
- sessão com `command`: `awaiting-input`, **não** fixo;
- sessão sem `command`: `idle`.

**`onInput()`**: `echoUntil = now + ECHO_WINDOW_MS`, e `sticky = false`. **O status não muda.** Quem responde a um pedido de permissão continua amarelo até o `claude` voltar a escrever depois da janela. Se o usuário digitar e não acontecer nada, nenhum timer está armado, e o estado fica onde está. Isso é correto: ninguém trabalhou.

**`onResize()`**: `resizeUntil = now + RESIZE_WINDOW_MS`. O status não muda.

**`onExit()`**: cancele o timer e vá para `exited`. Estado terminal.

Toda ida para um estado igual ao atual é silenciosa: `onChange` só dispara quando o `status` muda, e `since` só muda junto com ele.

## 5. Testes obrigatórios

Em `packages/daemon/src/status-detector.test.ts`, com `vi.useFakeTimers()` e `vi.setSystemTime`. Nenhum PTY. Os sinais entram como `TerminalSignal[]` literais, sem passar pelo parser.

1. **Cada aresta**, um teste por linha, cada uma com o `onChange` observado:
   - recém-construído e sem nenhuma chamada: sai de `running` em `quietMs`;
   - `running` → `awaiting-input` por silêncio, com `agent: true`, exatamente em `quietMs`: nada em `quietMs - 1`, transição em `quietMs`;
   - `running` → `idle` por silêncio, com `agent: false`;
   - `running` → `awaiting-input` fixo por `bell`, e por `notification`;
   - `running` → `idle` por marca `A`, `B` e `D`;
   - `idle` → `running` por saída;
   - `idle` → `awaiting-input` por `bell`;
   - `awaiting-input` (silêncio) → `running` por saída;
   - `awaiting-input` fixo → **fica** com saída; → `running` com marca `C`; → `idle` com marca `A`;
   - `awaiting-input` fixo → `onInput` → continua `awaiting-input` → saída depois da janela → `running`;
   - qualquer estado → `exited`, e depois de `exited` nenhuma chamada muda nada nem dispara `onChange`.
2. **Eco não pisca** (seção 3.1). Com `agent: true`, em `awaiting-input` por silêncio: vinte pares `onInput` + `onOutput([])` a cada 100 ms. **Zero** transições. Um `bell` dentro da janela também não transiciona. O mesmo `bell`, fora da janela, transiciona.
3. **Resize não pisca** (seção 3.2). Em `idle`: `onResize` + saída dentro de `RESIZE_WINDOW_MS` deixa em `idle`. Um `bell` dentro da janela de resize transiciona.
4. **Sinal e saída no mesmo chunk** (seção 3.3). `onOutput([{kind:'title'…}, {kind:'bell'}])` e `onOutput([{kind:'bell'}, {kind:'title'…}])` dão ambos `awaiting-input` fixo. Depois, 10 s de saída comum sem input, e continua `awaiting-input`.
5. **Comando longo sem saída em shell comum.** `agent: false`, marca `C`, depois silêncio longo: continua `running`. O mesmo com `agent: true` vira `awaiting-input`.
6. **O agente que saiu** (seção 2). `agent: true`, marca `D` e depois `A`, depois silêncio: `idle`. Sem marca nenhuma, o mesmo silêncio dá `awaiting-input`. Este teste **documenta a limitação**, não é bug.
7. **Um timer só.** Mil `onOutput([])` seguidos em `running` deixam `vi.getTimerCount()` em 1. Depois do `dispose()`, 0.
8. **Listener que lança.** Dois listeners, o primeiro lança: o segundo recebe a transição, e `onOutput` não propaga a exceção.
9. **`since`.** Com `vi.setSystemTime`, o `since` de cada transição é o instante dela, e uma chamada que não transiciona não o altera.

## 7. Fora de escopo

- Ligar o detector ao `onData`, ao `writeSessionInput`, ao `session.resize`, ao `session.status` e ao `SessionSummary.status`. É a M5.3.
- Ler `quietMs` por perfil do `config.json`: o config ainda não chega ao daemon (pendência do M4). A M7.1 liga.
- Qualquer mexida na configuração do Claude Code (decisão do dono, seção 1).
- Injetar shell integration (OSC 133) nos shells que o TermHub abre.
- Badges, animação e toasts (M5.4, M5.5).
