# Techspec — M5.1: parser de sinais do terminal (BEL e OSC)

Escrita no início do M5, sobre a `main` depois do merge do M4 (`60c42fd`). Esta spec é **normativa**: onde ela decide, não há escolha a fazer.

A M5.1 entrega um módulo puro, `packages/daemon/src/osc-parser.ts`, que lê o stream de saída de uma sessão e devolve os sinais que interessam ao detector de status (M5.2): bell, título, notificação, progresso e marcas de shell integration. Ninguém chama o módulo ainda. Ligar o parser ao `onData` da sessão é trabalho da M5.3.

## 1. O que o daemon recebe hoje: fatos medidos

Medido pelo coordenador em 26/09, no Windows 11 build 26200, com o `node-pty` do repo e as opções que o daemon usa (`useConptyDll` não informado, ou seja, o ConPTY do sistema). Um processo filho escreveu cada sequência entre marcadores de texto, e o daemon registrou o que chegou:

| Sequência emitida | Chega ao `onData`? | Observação |
|---|---|---|
| BEL `0x07` solto | sim | **fora de ordem**: vem no começo do quadro, antes do texto que a precedia |
| OSC 0 (título) | sim | fora de ordem, como o BEL |
| OSC 2 (título) | sim, **reescrita como OSC 0** | o ConPTY re-emite o título ele mesmo, sempre com `0;` e terminador BEL |
| OSC 9 (notificação), 9;9 (cwd), 9;4 (progresso) | sim | fora de ordem |
| OSC 777 `notify` | sim | fora de ordem |
| OSC 133 A/B/C/D | sim | **na ordem**, no meio do texto |
| OSC 633, OSC 99 | sim | fora de escopo (seção 6) |

Mais três fatos:

- O ConPTY emite um OSC 0 **próprio** logo depois do spawn, com o caminho do executável (`C:\Program Files\nodejs\node.exe`).
- O quadro inicial vem com `ESC[?9001h ESC[?1004h ESC[?25l ESC[2J`, sem nenhum sinal que interesse.
- Com `useConptyDll: true` tudo chega na ordem, e OSC 2 continua OSC 2. O daemon **não** usa essa opção, e esta tarefa não a muda.

Consequências para o desenho:

1. O parser só tem que acertar a **ordem do stream que recebe**. Não tente reconstruir a ordem original: ela não existe mais depois do ConPTY.
2. A M5.2 **não pode** tirar conclusões da posição de BEL, título ou OSC 9/777 em relação ao texto do mesmo chunk. Já o OSC 133 é confiável quanto à posição.
3. Builds mais antigos do Windows 10 podem engolir parte dessas sequências. O parser não depende disso: ele só deixa de ver o sinal, e a M5.2 cai no timer de ociosidade.

## 2. Três defeitos que esta spec evita

### 2.1 O título que vira bell

O jeito mais comum de encerrar um OSC é com o próprio BEL: `ESC ] 0 ; título BEL`. O `claude` troca o título o tempo todo enquanto trabalha, e o ConPTY reescreve todo título com terminador BEL (seção 1). Um parser que conta todo `0x07` como bell vê dezenas de bells por segundo num agente ocupado, e a M5.2 marca "esperando input" em quem está trabalhando. O mesmo vale para BEL dentro de DCS, SOS, PM e APC: lá dentro ele não toca nada.

**Um `0x07` só é bell quando o parser está fora de qualquer string de controle.** O teste que pega isso é o do título com terminador BEL, e o de BEL dentro de DCS e APC (seção 4).

### 2.2 A sequência partida entre chunks

O `onData` entrega o stream em pedaços arbitrários. `ESC ] 0 ; tí` num chunk e `tulo BEL` no seguinte são um título só. O caso traiçoeiro é o terminador ST (`ESC \`) partido entre o `ESC` e a `\`. O parser tem estado entre chamadas, e todo teste de sequência é repetido cortando o stream em **todos** os pontos possíveis (seção 4, teste 3).

### 2.3 O OSC que nunca termina

Um programa que escreve `ESC ]` e morre, ou que escreve lixo binário, deixa o parser dentro de uma string de controle para sempre. Dois cuidados:

- **Memória limitada.** O payload acumulado tem teto (`MAX_OSC_PAYLOAD = 4096` unidades UTF-16). Passou do teto, o parser para de acumular, continua no estado de OSC até o terminador, e ao terminar **não** emite evento. Sem teto, um daemon de vida longa acumula megabytes por sessão.
- **Mesma saída que o terminal.** O xterm do usuário também está preso no OSC e não mostra nada do texto seguinte. Um BEL nesse texto não é bell para o usuário, e não é para o parser. O parser sai do OSC exatamente onde o xterm sai (seção 3.2), nem antes nem depois.

### O passthrough não é problema deste módulo, por construção

O `milestones.md` pede "sem alterar o passthrough". A decisão é que o parser **só observa**. `feed()` recebe o chunk e devolve eventos, e **nunca** devolve bytes. O stream que vai para o buffer headless e para os clientes não passa por ele. Não crie função de "limpar" ou "filtrar" sequência, nem opção para isso: sujar o terminal do usuário com escape quebrado fica impossível, em vez de só testado.

## 3. A decisão: implemente exatamente assim

### 3.1 Duas camadas no mesmo arquivo

```ts
/** Maximum OSC payload kept, in UTF-16 code units. Longer OSCs emit nothing. */
export const MAX_OSC_PAYLOAD = 4096;

/** Low-level output of the scanner: exactly what a terminal would dispatch. */
export type RawSignal =
  | { type: 'bell' }
  | { type: 'osc'; id: number; payload: string };

/** Stateful tokenizer. One instance per session; never shared. */
export class SignalScanner {
  /** Scans one chunk. Synchronous, never throws, returns signals in stream order. */
  feed(chunk: string): RawSignal[];
  /** Length of the OSC payload currently being accumulated (0 outside an OSC). For tests. */
  get pendingPayloadLength(): number;
}

export type TerminalSignal =
  | { kind: 'bell' }
  | { kind: 'title'; title: string }
  | { kind: 'notification'; source: 'osc9' | 'osc777'; title: string | null; body: string }
  | { kind: 'progress'; state: 0 | 1 | 2 | 3 | 4; value: number | null }
  | { kind: 'shell-mark'; mark: 'A' | 'B' | 'C' | 'D'; exitCode: number | null };

/** Pure. Maps one dispatched OSC to a signal, or null when it is not one we use. */
export function interpretOsc(id: number, payload: string): TerminalSignal | null;

/** Scanner + interpretation. This is what M5.3 wires to `Session.onData`. */
export class TerminalSignalParser {
  feed(chunk: string): TerminalSignal[];
}
```

Contrato:

- **Síncrono e sem exceção.** `feed` é chamado dentro do `onData`, e uma exceção ali derruba a entrega do stream. Entrada malformada nunca lança: vira ausência de evento.
- **Uma passada, sem regex no chunk inteiro.** O stream de um agente chega a MB/s. Laço com `charCodeAt`. No estado de texto normal, nada é copiado. O payload de OSC é acumulado por fatias (`slice` do trecho contíguo), não caractere a caractere.
- **Estado próprio de cada instância**, sem nada global. Não há `reset()` nem `dispose()`: a instância morre junto com a sessão.
- `TerminalSignalParser.feed` devolve `interpretOsc` aplicado a cada `RawSignal` do tipo `osc`, descartando os `null`, e `{ kind: 'bell' }` para cada bell, na ordem.

### 3.2 O scanner copia a máquina do xterm.js, só no que importa

A referência é o `EscapeSequenceParser` do xterm.js (`node_modules/@xterm/xterm/src/common/parser/EscapeSequenceParser.ts`), que é o que o usuário vê na tela. O scanner reproduz dele **só o que decide onde começam e terminam as strings de controle**, com cinco estados:

| Estado | Entra por | Sai por |
|---|---|---|
| `ground` | início; fim de qualquer sequência | — |
| `escape` | `ESC` (`0x1B`) em qualquer estado | ver abaixo |
| `escapeIntermediate` | em `escape`, `0x20`–`0x2F` | `0x30`–`0x7E` → `ground` |
| `oscString` | em `escape`, `]`; ou C1 `U+009D` em qualquer estado | terminador (abaixo) |
| `ignoredString` | em `escape`, `P` (DCS), `X` (SOS), `^` (PM), `_` (APC); ou C1 `U+0090`, `U+0098`, `U+009E`, `U+009F` em qualquer estado | `ESC`, `U+009C`, CAN, SUB, outros C1 (abaixo) |

Regras que valem **em qualquer estado** (as "anywhere" do xterm):

- `ESC` → `escape`. Se estava em `oscString`, o OSC é **despachado com sucesso** antes, qualquer que seja o caractere seguinte. É o que o xterm faz: `ESC ] 9 ; oi ESC [ m` despacha o OSC 9 com `oi`. Por isso o ST (`ESC \`) funciona sozinho: o `ESC` despacha, e a `\` em `escape` volta para `ground` sem efeito.
- CAN (`0x18`) e SUB (`0x1A`) → `ground`. Um OSC em curso é **abortado**, sem evento.
- `U+009C` (ST em C1) → `ground`. Um OSC em curso é despachado.
- `U+009D` → `oscString`, `U+0090`/`U+0098`/`U+009E`/`U+009F` → `ignoredString`, e `U+009B` (CSI em C1) → `ground`. Um OSC em curso é abortado.
- Os outros C1 (`U+0080`–`U+008F`, `U+0091`–`U+0097`, `U+0099`, `U+009A`) → `ground`. Um OSC em curso é abortado.

Regras por estado:

- **`ground`**: `0x07` emite `bell`. O resto é texto e é ignorado.
- **`escape`**: `]` → `oscString`; `P`, `X`, `^`, `_` → `ignoredString`; `0x20`–`0x2F` → `escapeIntermediate`; `0x07` emite `bell` e **permanece** em `escape` (C0 é executado em `escape` no xterm); `0x7F` é ignorado e permanece; qualquer outro `0x30`–`0x7E` → `ground`. O CSI (`ESC [`) cai aqui como qualquer final: o scanner não precisa de estado de CSI, porque dentro de um CSI o xterm também executa o BEL como bell, e o final de um CSI (`0x40`–`0x7E`) volta para `ground` do mesmo jeito que o texto.
- **`escapeIntermediate`**: `0x07` emite `bell` e permanece; mais `0x20`–`0x2F` permanecem; `0x30`–`0x7E` → `ground`.
- **`oscString`**: `0x07` **despacha** o OSC e vai para `ground`. **Não é bell** (seção 2.1). Os outros C0 (`0x00`–`0x06`, `0x08`–`0x17`, `0x19`, `0x1B`–`0x1F`, menos os terminadores já citados) são **descartados**, e não entram no payload, como no xterm. Todo o resto entra no payload, inclusive `0x7F` e qualquer caractere a partir de `U+00A0`.
- **`ignoredString`**: tudo é ignorado, inclusive `0x07`, até uma das saídas "anywhere".

O despacho de um OSC separa o identificador do payload como o xterm: os dígitos antes do primeiro `;` são o `id`, e o resto, depois do `;`, é o payload. Sem `;`, o payload é `''`. Qualquer não-dígito antes do primeiro `;`, ou nenhum dígito, aborta, e não há evento. Um OSC que estourou `MAX_OSC_PAYLOAD` também não gera evento.

Onde o xterm e esta tabela divergirem, **o xterm está certo**. O teste diferencial (seção 4, teste 7) existe para achar isso. Achou divergência: corrija o scanner e reporte na entrega. Não ajuste o teste.

### 3.3 A interpretação

`interpretOsc(id, payload)`:

- **`0` e `2`** → `title` com o payload inteiro, inclusive vazio. O `1` (nome do ícone) é ignorado.
- **`9`** tem dois donos. O iTerm2 usa `9;mensagem` para notificação. O ConEmu, e o Windows Terminal que herdou dele, usa `9;N;...` para comandos: `9;9;cwd` é emitido **a cada prompt** por shells configurados para o Windows Terminal. Regra: se o payload casa com `^\d+(;|$)`, é comando do ConEmu, e nunca notificação. Entre esses, só `4` é interpretado, como `progress`: `9;4;estado[;valor]`, com o estado de `0` a `4` e o valor inteiro de `0` a `100`, ou `null` se ausente ou fora da faixa. Estado inválido dá `null`. Os outros comandos do ConEmu dão `null`. Qualquer outro payload é `notification` com `source: 'osc9'`, `title: null`, `body` igual ao payload inteiro. Payload vazio dá `null`. Uma mensagem de verdade que comece com `4;` perde, e o ConEmu ganha: sem essa regra, todo prompt vira um toast.
- **`777`** → só o subcomando `notify`. `notify;título;corpo` dá `notification` com `source: 'osc777'`. O título é o trecho até o próximo `;`, e o corpo é **todo** o resto, que pode conter `;`. `notify;título`, sem corpo, dá `body: ''`. Outros subcomandos (`precmd`, `preexec` e similares) dão `null`.
- **`133`** → `shell-mark` com a primeira letra do payload, se for `A`, `B`, `C` ou `D`. Os parâmetros depois do `;` são ignorados (`133;A;cl=m;aid=12`), exceto no `D`: `133;D;0` dá `exitCode: 0`, `133;D;130` dá `130`. Qualquer valor não inteiro ou ausente dá `null`. Letra fora de `A`–`D` dá `null`.
- Qualquer outro `id` → `null`.

## 4. Testes obrigatórios

Em `packages/daemon/src/osc-parser.test.ts`. Nenhum abre PTY: o módulo é puro.

1. **Cada sinal, isolado.** Um caso por linha da seção 3.3, nas duas formas de terminador (BEL e `ESC \`), e ao menos um caso com C1 (`U+009D … U+009C`).
2. **BEL como terminador não é bell.** `ESC]0;título BEL` produz exatamente `[title]`, sem nenhum `bell`. BEL dentro de DCS (`ESC P … BEL … ESC \`) e dentro de APC produz **zero** eventos. É o teste da seção 2.1, e ele **quebra** um scanner que emite bell em todo `0x07`: confira isso na entrega, trocando temporariamente a regra do `oscString` e mostrando o teste vermelho.
3. **Toda divisão possível.** Para cada stream de fixture dos testes 1 e 2, e para um stream longo que junta todas elas com texto no meio: para todo `i` de `0` a `length`, `feed(s.slice(0, i))` seguido de `feed(s.slice(i))` numa instância nova produz os mesmos eventos que `feed(s)`. Num stream curto que tenha ST, faça o mesmo em três pedaços, com todo par `i < j`. Inclua um caso nomeado com o corte exatamente entre o `ESC` e a `\` do ST, que emite o título **uma vez**.
4. **OSC sem terminador.** `ESC]0;` seguido de 1 MB de texto sem terminador: `pendingPayloadLength` nunca passa de `MAX_OSC_PAYLOAD`, e nenhum evento sai. Depois um BEL: nenhum evento, porque é o terminador do OSC estourado. Depois `BEL` outra vez, em `ground`: um `bell`. Um segundo caso: OSC em curso, CAN, BEL, que dá **um** `bell` e nenhum título.
5. **O OSC 9 do ConEmu.** `9;9;C:\x`, `9;4;1;50` (progresso `1`, `50`), `9;4;0` (progresso `0`, `null`), `9;4;9;50` (`null`), `9;oi` (notificação). E um stream que imita um prompt do Windows Terminal (`9;9` + `133;A` + texto + `133;B`), que produz zero notificações.
6. **Payload com C0 e com Unicode.** `ESC]0;a\x01b BEL` produz o título `ab`. Um título com acento e um emoji fora do BMP, partido no meio do par substituto por um corte do teste 3, volta inteiro.
7. **Diferencial contra o xterm.** O oráculo é o `@xterm/headless`, que já é dependência do daemon. Crie o `Terminal` com `allowProposedApi: true`, registre `onBell` e `parser.registerOscHandler(id, handler)` para os ids `0`, `2`, `9`, `133` e `777`, com o handler devolvendo `false` e gravando `(id, data)`, e colete a sequência de eventos na ordem. Um gerador com semente fixa (PRNG simples no próprio teste, sem dependência nova) monta ao menos 2000 streams a partir de um alfabeto de pedaços: `ESC`, `]`, `\`, `[`, `P`, `_`, `BEL`, CAN, SUB, `U+009C`, `U+009D`, `U+0090`, `;`, dígitos, os ids acima, `A`–`D`, letras, `\x01` e espaço. Cada stream é entregue ao scanner em pedaços aleatórios, e ao xterm inteiro, esperando o callback do `write`. Os bells e os `(id, payload)` filtrados para esses ids têm que ser **idênticos** nos dois. Os payloads gerados ficam abaixo de `MAX_OSC_PAYLOAD`, porque o teto do xterm é outro (10 MB). Em caso de falha, a mensagem mostra a semente e o stream com os controles escapados.

   Isto foi conferido pelo coordenador antes de escrever a spec: o headless dispara `onBell` e os handlers de OSC nesta versão, e trata BEL em DCS/APC, ESC solto encerrando OSC e CAN abortando exatamente como a seção 3.2 descreve.
8. **Custo.** 10 MB de texto comum com um OSC a cada 4 KB, em chunks de 16 KB, processados em menos de 2 s. É teto contra regressão grosseira (regex, concatenação por caractere), não benchmark.

## 6. Fora de escopo

- Ligar o parser ao `onData` da sessão, qualquer mudança em `service.ts`, `session.ts`, `buffer.ts` ou no protocolo. É a M5.3.
- Decidir estado (`running`, `awaiting-input`…) a partir dos sinais. É a M5.2.
- OSC 633 (shell integration do VS Code), OSC 99 (notificação do kitty), OSC 7 e `9;9` como cwd, OSC 1337. Chegam ao daemon (seção 1), mas ninguém pediu. Ficam como pendência para depois do M5.
- Trocar o `useConptyDll` da sessão.
