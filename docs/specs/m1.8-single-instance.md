# Techspec — M1.8: entrypoint do daemon e lock de instância única

Escrita depois que M1.2 a M1.7 fecharam, sobre o código como ele ficou. Esta spec é **normativa**: onde ela decide, não há escolha a fazer.

Esta é a tarefa que fecha o **gate do M1**.

## 1. O problema

O daemon é spawnado pela UI. Dois apps abrindo ao mesmo tempo — ou um app reabrindo enquanto o anterior ainda não morreu — não podem resultar em dois daemons.

A implementação que todo mundo escreve primeiro é:

```ts
if (!fs.existsSync(daemonJsonPath)) {
  startDaemon();
}
```

Isso não é um lock. É uma checagem seguida de uma ação, com uma janela entre as duas. Dois processos leem "não existe" no mesmo instante e os dois sobem um daemon.

## 2. O modo de falha que importa — e não é "dois daemons rodando"

Se fosse só desperdiçar um processo, seria chato e não grave. O estranho de verdade é o que acontece com o **token**.

Cenário: A e B sobem juntos. A vence a corrida pelo pipe. B perde — mas B já gerou o próprio token e escreveu o próprio `daemon.json`, sobrescrevendo o de A.

Agora: o daemon vivo é o de A, que só aceita o token de A. Todos os clientes leem o `daemon.json` de B e apresentam o token de B. **Todos são rejeitados no handshake.**

O sintoma é um daemon visivelmente rodando, sessões vivas lá dentro, e a UI insistindo que não consegue conectar. Ninguém olha para "corrida na inicialização" ao investigar isso — olham para o handshake, para o pipe, para o firewall.

Daí a regra da seção 3.2: **nada é escrito em disco antes de a corrida estar ganha.**

## 3. A decisão — implemente exatamente assim

### 3.1 O `listen()` no pipe é o lock

Não existe checagem de arquivo decidindo se o daemon sobe. A sequência é:

1. Resolver o endereço do pipe com `resolvePipeAddress()` (`transport-address.ts`).
2. Chamar `server.listen()`.
   - **Sucesso** → este processo é o daemon. Siga.
   - **`EADDRINUSE`** → outro daemon já é dono do pipe. Encerre **limpo**, com código de saída próprio e distinto (use `3`), sem tocar em `daemon.json`, sem retry, sem log de erro assustador. Perder a corrida é um desfecho previsto, não uma falha.
   - **Qualquer outro erro** → falha de verdade. Propague.

Criar um named pipe com nome já em uso é atômico no SO. É por isso que ele é o lock, e `existsSync` não.

Detecte `EADDRINUSE` **especificamente**, pelo `code` do erro. Não trate "qualquer erro do listen" como "outro daemon ganhou" — isso transformaria um bug real em encerramento silencioso.

### 3.2 A ordem da escrita em disco

**Só depois** de o `listen()` ter resolvido com sucesso:

1. gerar o token (`crypto.randomBytes`, hex, no mínimo 32 bytes);
2. escrever `daemon.json` **atomicamente** — arquivo temporário no mesmo diretório e `rename`, nunca escrita direta no destino;
3. registrar o serviço e armar o timer de ociosidade.

Quem perdeu a corrida nunca chega ao passo 1. Isso é o que impede o cenário da seção 2.

Conteúdo do `daemon.json`, em `%APPDATA%/TermHub/`:

```jsonc
{
  "pid": 12345,
  "pipe": "\\\\.\\pipe\\termhub-<hash>",
  "token": "<hex>",
  "protocolVersion": 1,
  "startedAt": "2026-09-21T13:00:00.000Z"
}
```

### 3.3 O furo que existe hoje no `listen()` — corrija

`TransportServer.listen()` chama `removeStaleSocketFile(address)` antes de escutar. No Windows ela retorna de cara, então o lock funciona. **Fora do Windows ela dá `unlink` incondicional no caminho do socket** — inclusive quando há um daemon vivo escutando nele. O segundo daemon apagaria o socket do primeiro e escutaria com sucesso: **o lock falha em silêncio**, e os clientes do primeiro daemon ficam pendurados num socket que não existe mais.

O projeto é "Windows primeiro, código cross-platform". Isso é uma bomba-relógio para o dia em que alguém rodar no Linux.

Corrija assim: antes de dar `unlink`, **sonde** o caminho tentando conectar nele.

- conexão aceita → há daemon vivo. **Não apague.** Deixe o `listen()` falhar com `EADDRINUSE`, que é o comportamento correto;
- `ECONNREFUSED` → socket órfão de processo morto. Aí sim apague e siga;
- `ENOENT` → não existe nada. Siga.

Você **está autorizado** a alterar `transport-server.ts` para isso, e apenas para isso.

### 3.4 Encerramento por ociosidade

O daemon se encerra sozinho quando, **ao mesmo tempo**:

- não há nenhum cliente conectado, **e**
- não há nenhuma sessão viva.

Default de 10 minutos, configurável.

**Sessão viva segura o daemon mesmo sem nenhum cliente.** Essa é a premissa inteira do produto: fechar a janela não mata os agentes. Um daemon que se encerra "porque ninguém está olhando" mata os cinco agentes do usuário — o exato oposto do que o TermHub existe para fazer.

Reavalie a condição a cada desconexão de cliente e a cada saída de sessão. Arme o timer quando ela passar a valer; cancele assim que um cliente conectar ou uma sessão for criada.

### 3.5 Encerramento limpo

Em `SIGINT`/`SIGTERM` e no caminho de ociosidade:

1. encerrar as sessões vivas (elas são filhas deste processo; sair sem matá-las deixa `conhost`/shell órfãos);
2. `server.close()`;
3. remover o `daemon.json` **somente se ele for nosso** — leia o arquivo e compare o `pid` com o nosso. Se não bater, outro daemon já assumiu; não apague o dele.

Em crash não há limpeza, e não tem problema: o pipe morre com o processo, então um cliente que tente conectar recebe `ENOENT` e sabe que precisa subir um novo daemon. O `daemon.json` órfão é resolvido pela seção 3.2 — o próximo daemon o sobrescreve **depois** de ganhar o lock.

### 3.6 O `cli.ts` — o gate do M1

Um cliente de linha de comando para diagnóstico, que executa o gate do milestone:

1. sobe (ou conecta ao) daemon;
2. cria uma sessão;
3. manda `echo hi` **como frame binário**, via `client.sendData`;
4. espera o `hi` chegar na saída;
5. **desconecta**;
6. **reconecta** e faz `session.attach`;
7. imprime o buffer recebido, que deve conter o `hi`.

Atenção ao contrato da M1.7: **instale o handler de dados antes de chamar `session.attach`** — o snapshot chega como frame binário, antes da resposta do RPC.

## 4. Assinaturas e contratos

```ts
// daemon.json
interface DaemonInfo {
  pid: number;
  pipe: string;
  token: string;
  protocolVersion: number;
  startedAt: string;
}

// entrypoint
type StartResult =
  | { outcome: 'started'; info: DaemonInfo }
  | { outcome: 'already-running' };   // perdeu a corrida: exit code 3
```

O entrypoint precisa ser testável sem spawnar processo: exponha a função de start recebendo o endereço do pipe e o caminho do `daemon.json` por parâmetro, com os defaults reais. Testes de corrida vão chamá-la duas vezes em paralelo, no mesmo processo, com um endereço único.

## 5. Testes obrigatórios

Os três primeiros são o motivo desta spec existir.

1. **A corrida.** Duas chamadas de start **em paralelo**, no mesmo endereço de pipe: exatamente uma devolve `started`, a outra devolve `already-running`. Não sequencie as chamadas — dispare as duas e só então dê `await` nas duas; sequencial não testa corrida nenhuma.
2. **A perdedora não escreve nada.** No mesmo cenário, prove que o `daemon.json` final contém o token e o pid da **vencedora**. É o teste que pega o modo de falha da seção 2, e que uma implementação com `existsSync` passa por acaso metade das vezes.
3. **A sonda de socket órfão** (seção 3.3): com um servidor vivo escutando, uma segunda tentativa de `listen()` no mesmo endereço **falha com `EADDRINUSE`** e o socket do primeiro **continua funcionando** — prove mandando um RPC pelo cliente já conectado, depois da tentativa.
4. `daemon.json` órfão, com `pid` de processo morto, não impede um daemon novo de subir, e é sobrescrito com os dados corretos.
5. A escrita do `daemon.json` é atômica: não existe janela em que o arquivo esteja truncado ou pela metade.
6. **Ociosidade não mata sessão viva.** Com zero clientes mas uma sessão viva, o daemon **não** encerra. Com zero clientes e zero sessões, encerra depois do timeout. Use fake timers.
7. Encerramento limpo remove o `daemon.json`; encerramento de um processo cujo pid **não** bate com o do arquivo não o remove.
8. **O gate do M1, ponta a ponta:** criar sessão, `echo hi` por frame binário, desconectar, reconectar, anexar, e o buffer recebido contém o `hi`. Este é o critério de aceite do milestone inteiro.
9. Os 85 testes existentes continuam verdes.

Nenhum processo de shell órfão ao fim da suíte.

## 6. Fora de escopo

- O lado do cliente: spawn do daemon com `ELECTRON_RUN_AS_NODE`, backoff, detecção de daemon zumbi que aceita conexão e não responde → **M2.1**.
- Cemitério com TTL → M4.4. Detecção de status de agente → M5.
- ACL do named pipe. O token é a autenticação, e o `daemon.json` mora em `%APPDATA%`, que o NTFS já restringe ao usuário. Endurecer o descritor de segurança do pipe é trabalho de segurança para depois, não desta tarefa — mas **não escreva comentário afirmando que o pipe está restrito ao usuário**, porque não verificamos isso.
